# ۰۷ — کارایی، حافظه و برنامهٔ بنچمارک

هدف: روی هر دستگاه، **بهترین کیفیت در بودجهٔ زمانی قابل‌قبول**. عدد بدون اندازه‌گیری ممنوع.

---

## ۱. مدل ذهنی هزینه

```
T_total ≈ T_decode + Σ_stages (MP_work × t_stage) + T_encode
MP_work = (W_in × H_in × scale²) / 1e6
t_stage = ms per output-megapixel for that model/backend
```

`t_stage` تابع: مدل، دقت (FP32/FP16/INT8)، اندازهٔ کاشی، بک‌اند، و **هم‌پوشانی** (overlap هزینهٔ ~۱۰–۲۰٪ اضافه دارد).

## ۲. کوانتیزه‌سازی و انتخاب دقت

| دقت | سرعت | حافظه | کیفیت | کجا |
|---|---|---|---|---|
| FP32 | ۱x | ۱x | مرجع | CPU بدون AVX512، دیباگ |
| FP16 | ۲–۴x | ۰.۵x | ~بدون افت | Vulkan/Metal/DirectML (اگر پشتیبانی شود) |
| BF16 | ۲–۳x | ۰.۵x | ~بدون افت | NPU/دستگاه‌های جدید |
| INT8 | ۳–۶x | ۰.۲۵x | افت کم (کالیبره) | CPU/موبایل؛ با شرط افت LPIPS < ۲٪ |

قواعد:

- FP16 فقط اگر `caps.fp16` و بنچمارک واقعاً سریع‌تر باشد (بعضی iGPUها FP16 را کند اجرا می‌کنند).
- INT8 با **calibration** روی ۵۰۰ تصویر متنوع؛ بدون calibration استفاده نکن.
- مدل‌های حساس (face, matting) با FP16، نه INT8.

## ۳. بهینه‌سازی‌ها (به ترتیب اثر)

1. **کاهش کار انجام‌شده**: پیش‌کوچک‌سازی تا ابعاد هدف؛ پرهیز از ۱۶x وقتی هدف ۴K است (۸x کافی است). این بزرگ‌ترین برد است.
2. **Tiling هوشمند**: tile بزرگ‌تر = سرعت بیشتر (کمتر overlap) تا وقتی OOM نشود.
3. **Zero-copy** بین مراحل (بافر مشترک، بدون realloc).
4. **Winograd/FFT convolution** (ncnn خودکار در برخی مدل‌ها).
5. **اجرای موازی مدل‌های مستقل** (مثلاً face detection و تحلیل محتوا هم‌زمان با SR کاشی اول).
6. **پرهیز از CPU↔GPU transfer** در هر کاشی؛ پردازش بچ‌شدهٔ چند کاشی در یک submit.
7. **کش نتایج** برای پیش‌نمایش تعاملی و A/B.
8. **کدگذاری موازی** (encode در thread جدا، هم‌زمان با کاشی بعدی).
9. **حذف مراحل بی‌اثر**: اگر نویز کم است، denoise را رد کن (Analyzer تصمیم می‌گیرد).
10. **Thread affinity** و `num_threads = physical_cores` (نه logical) روی CPU.

## ۶. کیفیت به‌عنوان معیار کارایی

اگر مدل ۲x سریع‌تر باشد ولی LPIPS ۱۰٪ بدتر، انتخاب نمی‌شود. جدول تصمیم:

```
score = w1·(−LPIPS) + w2·(−DISTS) + w3·OCR + w4·(−time_norm) + w5·(−peak_mem_norm)
```

وزن‌ها در `bench/config.json` قابل تغییر؛ برای هر تیر سخت‌افزاری مجموعهٔ متفاوتی از وزن‌ها (کاربر موبایل تحمل زمان کمتری دارد).

## ۷. گرمایش، باتری و تجربه

- **Warmup** یک‌باره بعد از بارگذاری مدل (۱–۲ کاشی کوچک) تا اولین تصویر کاربر کند نباشد.
- روی موبایل: اگر `thermalState >= SEVERE` → tile نصف، threads نصف، پیام «دستگاه گرم شده».
- حالت باتری: فقط ۲x و مدل سبک، مگر کاربر تغییر دهد.
- ETA با میانگین متحرک زمان کاشی محاسبه می‌شود (نه تخمین ثابت) و در UI با بازه نمایش داده می‌شود.
